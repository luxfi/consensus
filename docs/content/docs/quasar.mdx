# Quasar

Quasar is two things that share a name because they are the same claim at two
strengths.

**The rung.** On the [finality ladder](/docs/standard#the-ladder), quasar is the
rung where a certificate exists whose distinct signers hold strictly more than two
thirds of stake. It is the export boundary: bridges, DEX settlement, cross-chain
messages and validator-set transitions read quasar and nothing below it.

**The package.** `protocol/quasar` is the post-quantum apparatus that carries the
same relation with post-quantum cryptography, which is what takes a block from
quasar to horizon.

The finality *rule* is identical at both. Only the cryptography of the witness
differs, and that is the whole design: one rule, an orthogonal witness format.

## Two witnesses, one relation

The engine-level `QuorumCert` in `engine/chain` keys voters by `ids.NodeID`, each
carrying one signature over the canonical vote message, and needs only a pluggable
`VoteVerifier`. That is what every chain — P, X, C, D — runs today on every
deployment, with no extra plumbing.

`quasar.WeightedQuorumCert` witnesses the same relation with the heavyweight
apparatus. Signers are leaves of the epoch's weighted validator set, each carrying
a FIPS 204 / FIPS 205 record and a Merkle inclusion proof against the set root. It
needs three pieces of node-layer state the engine does not own: the epoch's
weighted-set Merkle root, each validator's post-quantum public-key leaf and voting
weight, and per-validator Merkle paths.

When a chain has those plumbed through, the engine certificate upgrades to carry
the weighted certificate as its witness — no change to the rule. When it has not,
the source is nil and the engine certificate remains the witness. Same rule,
lighter witness. The bridge between them is `engine/chain/quasar.go`; no
cryptography is invented at the engine level.

## What the weighted certificate proves

A quorum-weight subset of the epoch validator set each produced a valid,
**independent** FIPS 204 / 205 signature over the same domain-separated message.
Verification is direct — there is no succinct proof layer between the reader and
the signatures:

```text
for each signer record:
  (a) the leaf is included under validator_set_root      (Merkle)
  (b) the parameter set is in the allowed set
  (c) the signature verifies under the stock FIPS verifier
  (d) validator ids are strictly increasing              (distinct, canonical)
accumulate weight; then
  Σ weight ≥ quorum_threshold
  Σ weight == aggregate_weight
  commit(signer_ids) == signer_commitment
```

Soundness rests on exactly two things: unmodified FIPS 204/205 verification — each
signature is byte-identical to what the NIST reference accepts — and the
second-preimage resistance of the weighted-set Merkle commitment.

This is threshold **certification**, not threshold signing. There is no DKG, no
seed or WOTS+ or FORS or secret share ever combined or exposed. No private key
material is shared or reconstructed. Building a certificate therefore needs no
secret: a node collects already-produced signer records, sorts them, and assembles.
Any node with the records builds the identical certificate — permissionless and
leaderless, the same property the engine certificate has.

## The legs

A Quasar certificate carries independent signing paths, run in parallel rather than
in sequence:

| Leg | Primitive | Hardness |
|---|---|---|
| BLS | BLS12-381 aggregate | ECDL — classical fast path, empty in pure-PQ |
| Pulsar | Module-LWE threshold | Module-LWE |
| Corona | Ring-LWE threshold | Ring-LWE |
| Magnetar | SLH-DSA (FIPS 205) | hash-based |
| ML-DSA rollup | per-validator ML-DSA-65 (FIPS 204) | Module-LWE + Module-SIS |

Corona and Pulsar together are the honest post-quantum cardinality: two independent
algebraic-lattice families, each independently a FIPS 204 class threshold producer.
BLS is irrelevant to that predicate by design — a pure-PQ certificate carries no
BLS bytes; a hybrid certificate layers BLS over the post-quantum surface.

An adversary against the full set must break ECDL *and* Module-LWE *and*
Module-SIS at once.

## Postures

An operator does not assemble legs by hand. A chain selects a posture, and the
posture pins both the required leg kinds and the permitted modes for them:

| Posture | Requires | For |
|---|---|---|
| `BLS_FAST` | BLS | mempool, fast local acceptance |
| `HYBRID_PQ_CHECKPOINT` | BLS ∧ (Pulsar ∨ ML-DSA rollup) | checkpoints |
| `STRICT_QUASAR` | BLS ∧ Pulsar ∧ Corona | dual-lattice strict finality |
| `RECOVERY_MODE` | BLS ∧ ML-DSA rollup | recovery, migration, bridge — no Pulsar key |
| `POLARIS_HASH_PQ` | BLS ∧ Pulsar ∧ Magnetar rollup | adds hash-based diversity |
| `POLARIS_MAX` | BLS ∧ Pulsar ∧ Corona ∧ Magnetar rollup | Module-LWE ∥ Ring-LWE ∥ hash-based |

The Polaris postures admit Magnetar only as the trustless rollup — independent
per-validator FIPS 205 signatures with no dealer, no DKG, no shared secret. A
threshold mode with a signing-time trusted component is never admitted, because
SLH-DSA cannot be proven by a threshold signature.

The required leg kinds commit the *requirement*; the policy id and its allow-table
commit the *mechanism*. `HYBRID` and `RECOVERY` require the same kinds and are
distinguished only by which modes they permit.

## The quantum transition

Before quantum computers, the model is ordinary Byzantine fault tolerance and the
BLS aggregate is a fast classical path.

When BLS becomes forgeable, the lattice and hash-based legs do not. A block whose
post-quantum legs do not verify is not final at horizon, whatever its BLS bytes
say. The network stalls rather than accepting an unsafe fork — which is the correct
behaviour for an export boundary, and the reason the ladder keeps horizon distinct
from quasar instead of folding the two together.

## Accelerator dispatch

Each primitive routes batch operations through `crypto/backend.Resolve` to
`accel.LatticeOps` when a GPU backend is selected or auto-detected. Single
signatures stay on CPU: kernel-launch overhead exceeds the win at n = 1. The
aggregated certificate verify path is the one that benefits and dispatches
accordingly.
